# Release Process

This repository's own `.github/workflows/*.yml` each call into a *reusable* workflow hosted in a separate repository, [`abofs/stonyx-workflows`](https://github.com/abofs/stonyx-workflows), pinned at `@main` (a branch ref, not a pinned tag or SHA). **That is the boundary of what is verifiable from inside this repo.** Everything below the line in each section is read directly from this repo's workflow YAML and `package.json`; the actual version-bump, publish, and cascade *logic* lives in `stonyx-workflows` and was not inspected — per the scope of this task, infrastructure and another repository's internals are out of bounds here. Where the previous version of this document made a claim this repo's files cannot confirm, that is called out explicitly rather than repeated silently.

## What this repo's workflows declare

**CI — `.github/workflows/ci.yml`.** Triggers on `pull_request` targeting `dev`, `main`, or any `fix/**` branch. Runs with `permissions: contents: read` and a concurrency group keyed on the head ref (new pushes to the same PR cancel the in-flight run). The single job calls `abofs/stonyx-workflows/.github/workflows/ci.yml@main` with no inputs and no `secrets: inherit` — this job does not have access to repository secrets. What that reusable workflow actually runs (presumably `pnpm install` + `pnpm test` + `pnpm typecheck`, matching `prepublishOnly` below, but not confirmed from here) is defined outside this repo.

**Publish — `.github/workflows/publish.yml`.** Triggers on four distinct events: a `repository_dispatch` of type `cascade-publish` (fired by another package's release cascading into this one), a manual `workflow_dispatch` with a `version-type` choice (`patch`/`minor`/`major`) and an optional `custom-version` string override, `pull_request` (`opened`/`synchronize`/`reopened`) against `dev` or `main`, and `push` to `dev` or `main`. Concurrency is grouped as `cascade-update` for the dispatch trigger and `publish-<ref>` otherwise, and is **not** cancel-in-progress (`cancel-in-progress: false`), so overlapping publish runs queue rather than clobber each other. Permissions are `contents: write`, `id-token: write` (OpenID Connect — consistent with `package.json`'s `publishConfig.provenance: true`, npm provenance attestation), and `pull-requests: write`. Two jobs, both with `secrets: inherit`:
  - `publish` calls `abofs/stonyx-workflows/.github/workflows/npm-publish.yml@main` with `version-type`, `custom-version`, and `cascade-source` (populated from the dispatch payload's `source_package` when triggered by a cascade). It exposes `package-name` and `published-version` as outputs.
  - `cascade` (`needs: publish`) calls `abofs/stonyx-workflows/.github/workflows/cascade.yml@main`, passing those two outputs through. This is presumably what fires the `cascade-publish` `repository_dispatch` against downstream `@stonyx/*` module repos — matching `@stonyx/utils`'s own docs, which describe being on the receiving end of exactly this cascade — but the cascade workflow's own targets and triggering logic live in `stonyx-workflows` and were not inspected.

  **Unconfirmed from here:** what actually decides whether `push`/`pull_request` events on this workflow result in a real `npm publish`, versus a no-op or dry run. The reusable `npm-publish.yml` presumably gates that on the event type and the `version-type`/`custom-version` inputs (which are only populated by `workflow_dispatch`), but that gate is defined in `stonyx-workflows`, not here — merging a PR into `dev` triggers this workflow by this repo's own trigger list, and what it does next is an external claim, not something this repo's files confirm.

**Security audit — `.github/workflows/security-audit.yml`.** Runs on a daily `cron` schedule (`0 8 * * *`) and on manual `workflow_dispatch`, with `permissions: contents: read`. The single job calls `abofs/stonyx-workflows/.github/workflows/security-audit.yml@main`, which presumably runs `npm audit` / `pnpm audit` or similar against the dependency tree, but its actual checks are defined outside this repo and were not inspected.

## What `package.json` declares

**`prepublishOnly`: `pnpm build && pnpm test`.** This runs automatically before `npm publish` (whether invoked directly or by the `npm-publish.yml` reusable workflow, assuming that workflow calls `npm publish` rather than reimplementing the build/test step itself — not confirmed from here). It is the same `pnpm build` + `pnpm test` sequence verified independently in `docs/index.md`'s Build/Run/Test section: build succeeds, and the full QUnit suite (183 tests) passes. So whatever triggers an actual publish, the local gate it runs is proven to pass against the current `dev` HEAD. `test/unit/package-scripts-test.ts` asserts this exact command and fails if any script in `package.json` invokes npm, npx or yarn, keeping the scripts consistent with the "Always pnpm" convention in `docs/conventions/index.md`.

**Published contents** (verified with `npm pack --dry-run` against this checkout): `dist/` (the `tsc` build output), `config/environment copy.ts` and `config/environment copy.js` (the two postinstall templates), `scripts/postinstall.js`, and `README.md` — exactly what `package.json#files` declares — plus `package.json` and `LICENSE.md`, which npm always includes. This matches the previous version of this document, and the previous document's claim that nothing in the test suite guards the tarball's exact contents is also confirmed: no test in `test/**` reads `package.json#files` or runs `npm pack`. Anyone changing `files` should re-check with `npm pack --dry-run` by hand, exactly as the earlier doc said.

**`publishConfig.provenance: true`** — requests npm provenance attestation (ties the published artifact back to the GitHub Actions run that built it via OIDC). This is consistent with the `id-token: write` permission on `publish.yml`, but whether the reusable workflow actually performs an attestable publish (versus, say, a manual token-based one) is, again, defined in `stonyx-workflows`.

**Version**: this checkout is `0.2.3-beta.107`. The `dev` branch's own recent commit history (`chore: release v0.2.3-beta.107 [skip ci]`, `chore: release v0.2.3-beta.106 [skip ci]`, …) shows the release pipeline commits a version bump directly to `dev` with a `[skip ci]`-tagged message after each publish — consistent with a workflow that bumps `package.json#version`, commits, and tags, but the commit/tag mechanics themselves happen inside `stonyx-workflows` and were not inspected here.

## Discrepancies and unconfirmed claims, listed again

1. **The actual publish/version-bump/cascade logic is external and unverified.** Every one of this repo's three workflows is a thin wrapper around a reusable workflow in `abofs/stonyx-workflows@main`. This document only describes what triggers them and what permissions/inputs they're given from this repo's side; what they *do* was not inspected, per this task's scope (infrastructure and other repositories are off-limits).
2. **`abofs/stonyx-workflows@main` is a floating branch reference, not a pinned SHA or tag**, in all three workflow files. A change merged to that repo's `main` changes this repo's CI/publish/security-audit behavior immediately, with no version bump or review in *this* repo. That is a statement about what the YAML says, not a recommendation to change it.
3. **Whether a `push` to `dev` or a `pull_request` into `dev`/`main` actually performs an npm publish, versus a no-op/dry-run, is not confirmed from this repo's files.** The trigger list says these events invoke `publish.yml`; the gating logic that decides what happens next lives in the external reusable workflow.
4. **Provenance attestation (`publishConfig.provenance: true`, `id-token: write`) is declared but its actual execution is not confirmed** — that happens inside the external `npm-publish.yml` workflow.

None of the above are proposed to be fixed or filed as issues as part of this documentation pass — they are stated so the next reader does not inherit an unverified claim silently.
