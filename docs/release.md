# Release Process

This package follows the Stonyx shared release pipeline managed by [stonyx-workflows](https://github.com/abofs/stonyx-workflows).

See [stonyx-workflows/docs/release.md](https://github.com/abofs/stonyx-workflows/blob/main/docs/release.md) for the full release process, versioning scheme, and cascade publishing details.

**npm package:** `stonyx`

**Published contents:** `dist/`, `config/` (the two `environment copy` templates), `scripts/` (`postinstall.js` and the `postinstall-manifest.js` it imports) and `README.md`, per `files` in `package.json`; the packer adds `package.json` and `LICENSE.md`. `scripts/postinstall.js` runs on every consumer install, so keep it free of network and secret access.

**Pack-surface guard:** `test/unit/publish/pack-surface-test.ts` packs the tarball with `pnpm pack`, as the release job does, and fails on the defects listed below (abofs/stonyx#123). It reads `scripts` and `bin` from the tarball's own `package.json`, so `publishConfig` overrides count. It does not prove the tarball installs from the registry. Its dependencies resolve to the versions installed for this repo, and their own imports resolve from this repo's tree, so a `dependencies` version the registry does not serve passes here. CI's `pnpm install` is what catches an unpublished version: PR CI and normal publishes install with `--frozen-lockfile`, which fails with `ERR_PNPM_OUTDATED_LOCKFILE`; cascade publishes install with `--no-frozen-lockfile` (stonyx-workflows `npm-publish.yml:208`), which still fails, with `ERR_PNPM_NO_MATCHING_VERSION`. It checks that:

- `scripts.postinstall` and `scripts/postinstall-manifest.js` are in the tarball, and so is every template the manifest names;
- the shipped postinstall, run for a JS consumer and for a TS consumer with only the tarball's `dependencies` resolvable, exits 0 and writes `config/environment.{js,ts}`. It runs in an approximation of npm 11's install environment (see the residual below): cwd is the extracted package, `INIT_CWD` is the consumer, which has a `package.json` with the fields `npm init -y` writes, `npm_lifecycle_event` is `postinstall`, `npm_package_json` is the extracted `package.json` and `npm_config_user_agent` is npm 11's. The test runner's `npm_*`/`pnpm_*` variables, `NODE_PATH` and its `node_modules/.bin` entries on `PATH` are dropped;
- `preinstall` and `install` are not declared, so the postinstall is the only script a consumer install runs;
- `bin.stonyx` is in the tarball and starts with `#!/usr/bin/env node`;
- `prepack`, `prepare` and `postpack` are not declared. `pnpm pack` runs them in the release job, and the guard packs with scripts ignored. A declared `prepack` or `prepare` would make the release tarball differ from the guard's. A `postpack` runs after the tarball is written, so it does not change the tarball, but it changes the source tree in the release job, which the guard never sees.

**Residual:** the guard approximates npm's install environment; it does not reproduce it. It does not cover a postinstall that branches on environment variables, consumer fields or platform (`os`/`cpu`) beyond what it models: such a postinstall can pass the guard and fail `npm i`. stonyx's postinstall branches on none of these beyond what the guard models: it reads only `INIT_CWD` and `npm_config_global` from the environment and only `tsconfig.json` and `config/` from the consumer, all of which the guard sets, and `package.json` declares no `os`/`cpu`. The authoritative install check is the live `npm i` and `npm i -g` of `stonyx` from the registry in the Go/No-Go release checklist (abofs/stonyx#123, refinement validation assertions 2-3).

The template names live in `scripts/postinstall-manifest.js`, which both the postinstall and the guard import: to rename a template, change the file and the manifest together. The same names are also the consumer opt-out: the postinstall skips a consumer that ships its own `config/<template>` (abofs/stonyx#54, #62; `scripts/postinstall.js:21`). So renaming a template in the manifest also renames the file consumers must ship to opt out. That is a consumer-facing change, and the #54/#62 tests in `test/unit/postinstall-test.ts` go red on it.

Beyond this guard, the shared pipeline refuses a release artifact that has fewer than two entries, has no `package/package.json`, or contains a `.git` entry. Nothing else checks the tarball contents. After changing `files`, check the list by hand: `pnpm build` (`dist/` is gitignored, so without a build the tarball has no `dist/`), then `pnpm pack --pack-destination <tmp dir>`, then `tar -tzf <tmp dir>/stonyx-*.tgz`.
